# Phase 5.C — Offer EV Simulation Spine (Customer × Offer)

## Purpose of Phase 5.C

Phase 5.C answers the question:

> **“For the customers we allowed into the decision system, what does expected value (EV) look like under each offer — and does *anything* beat `no_offer`?”**

Phase 5.B was intentionally conservative: it created a *small, defensible* pool of `eligible_for_review` customers based on risk + value + structural cost logic.
Phase 5.C does **not** change eligibility. It builds the **simulation table** that makes decision ranking possible in Phase 5.D.

This step is important because it prevents the policy engine from making decisions off partial data or implicit assumptions. Every eligible customer must be evaluated under the same set of offer options, using the same EV framework from Phase 4.

---

## View Created

**`churn.v_6_phase_5_c_offer_ev_spine`**

### What this view represents

A fully expanded grid of:

* **each eligible customer anchor**
  ×
* **each offer type** (`no_offer`, `free_shipping`, `discount_5_percent`, `discount_10_percent`)
  → joined to:
* the corresponding Phase 4 EV row (cost, lift, p_offer, delta_p, net EV, etc.)

So the output is **one row per (customer_unique_id, anchor_date, offer_type)** for eligible anchors only.

This is the “decision-ready table” Phase 5.D will rank.

---

## How it works (CTEs in plain English)

### 1) `eligible`

Pulls only customers who passed Phase 5.B:

* `eligibility_status = 'eligible_for_review'`

This is the policy boundary. No one outside this set should reach Phase 5.D.

### 2) `offers`

Defines the set of offers that are worth considering.

Hard-coded on purpose:

* it keeps the policy stable
* it avoids accidental offer creep
* it guarantees that every eligible customer sees the same action menu

### 3) `expanded`

Cross-joins eligible anchors with the offer list:

* if you have **N eligible anchors** and **4 offers**, you should always get **4N rows**

### 4) Final join to `v_6_offer_ev`

Enriches each expanded row with EV fields computed in Phase 4:

* `offer_cost`
* `lift_default`
* `p_offer_default`
* `delta_p_default`
* `expected_offer_cost`
* `p_base_default`
* `net_ev_default`

And adds an explicit completeness flag:

* `is_missing_ev_row`
  (this is the “don’t let silent join failures ruin the decision engine again” guardrail)

---

## Why Phase 5.C matters (business logic)

Phase 5.C is where the system becomes *decision-grade*.

Without this spine:

* Offer per customer can’t be fairly compared
* Risk making decisions on incomplete joins (hidden NULLs)
* The policy (“we evaluated all options consistently”) can't be defended

With this spine:

* every eligible customer has a full menu of offers
* every offer is scored using the same EV framework
* Phase 5.D can safely rank offers and fall back to `no_offer`


---

## Transition to Phase 5.D

With `v_6_phase_5_c_offer_ev_spine` built and validated, the next question becomes:

> **“For each eligible customer, which offer maximizes net expected value — and should we still fall back to no_offer when the best EV is ≤ 0?”**

Phase 5.D will:

* rank offers by `net_ev_default` per customer anchor
* break ties conservatively (cheaper offers win)
* enforce a business-safe default:

  * if best EV is non-positive → choose `no_offer`
