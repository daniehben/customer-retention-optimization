# Phase 7A — Scenario definitions + scenario economics re-computation

## Purpose of Phase 7A

Phase 7 is about **stress-testing and governance**:

* There already exists an offer EV engine (Phase 5 / Phase 6).
* Now it is time to answer this business question:
  **“If our assumptions are wrong (margin shifts, lift shifts, shipping cost shifts), what happens to decisions and outcomes?”**

Phase 7A creates the **parameterized scenario framework** and recomputes **EV + cost** under each scenario, without changing your underlying customer and offer behavior tables.

---

## 7A.1 `churn.v_7a_scenario_params` — Scenario dictionary (the “control panel”)

### What this view is

A small, explicit “scenario catalog” table. It defines each scenario as a row with:

* `scenario_id`
* `margin` (profit margin assumption)
* `lift_multiplier` (strengthen/weaken lift)
* `shipping_cost_multiplier` (inflate shipping costs only)
* `budget_rate` (share of GP used as budget pool)

### Why this view exists (business)

This is what turns Phase 7 into **structured governance** instead of ad-hoc modifications.

* Easy to add new scenarios later.
* Ensures all downstream scenario logic is reproducible and auditable.
* Makes the final “why did scenario X win?” explainable.

### Output

A tiny table, 6 rows, one per scenario.

---

## 7A.2 `churn.v_7a_budget_pool_by_scenario` — Budget pool per scenario-month

### What this view is

This view calculates the **available budget** per month under each scenario using expected gross profit:

**Expected GP per anchor**
[
expected_gp_per_anchor = margin \times AOV_{pre_anchor} \times p_{reorder_180d}
]

Then aggregates monthly and applies the policy:

[
budget_amount = period_expected_gp \times budget_rate
]

### Inputs

* `churn.v_6_baseline_risk_segment` (customer anchors, AOV)
* `churn.v_6_p_base_by_risk_segment` (risk_segment → `p_reorder_180d`)
* `churn.v_7a_scenario_params` (scenario margin + budget_rate)

### Outputs

Per `(scenario_id, decision_month)`:

* `period_expected_gp` (the “budget base”)
* `budget_amount` (the “cash budget available”)
* `anchor_count` + `missing_p_rows` (data quality monitors)

### Why it matters

This is the **budget constraint source of truth** for Phase 7.

If this is wrong, allocation and scenario comparisons become meaningless.

---

## 7A.3 `churn.v_7a_offer_ev_by_scenario` — Recompute EV under each scenario

### What this view is

This is the **core scenario economics step**.

Starting from your “economics truth” spine (`churn.v_6_offer_ev`), you recompute the benefit/cost components under scenario assumptions:

#### A) Margin scenarios affect benefit

You scale margin value:

[
expected_margin_value_{scn} = expected_margin_value \times \frac{scenario_margin}{base_margin}
]

#### B) Lift scenarios affect incremental probability (delta_p)

You scale lift:

[
lift_{scn} = lift_{default} \times lift_multiplier
]

Then recompute:
[
p_{offer_{scn}} = min(1, p_{base} + lift_{scn})
]
[
delta_p_{scn} = p_{offer_{scn}} - p_{base}
]

#### C) Shipping scenarios affect cost only for free_shipping

Only `free_shipping` changes:

[
offer_cost_{scn} =
\begin{cases}
offer_cost \times shipping_cost_multiplier & \text{if free_shipping}\
offer_cost & \text{otherwise}
\end{cases}
]

#### D) Final EV recomputation (portfolio-grade)

You recompute EV from components instead of multiplying `net_ev_default`:

[
incremental_profit_{scn} = delta_p_{scn} \times expected_margin_value_{scn}
]
[
expected_offer_cost_{scn} = p_{offer_{scn}} \times offer_cost_{scn}
]
[
net_ev_{scn} = incremental_profit_{scn} - expected_offer_cost_{scn}
]

### Output

For each `(scenario_id, customer_unique_id, anchor_date, offer_type)` you get scenario-adjusted:

* `p_offer_scn`
* `delta_p_scn`
* `offer_cost_scn`
* `expected_offer_cost_scn`
* `net_ev_scn`

### Dependencies / Build Order

**Upstream dependencies (must exist first)**

* `churn.v_6_offer_ev` (economics truth spine: p_base_default, lift_default, expected_margin_value, offer_cost, net_ev_default)
* `churn.v_6_baseline_risk_segment` (customer anchors, risk_segment, aov_pre_anchor)
* `churn.v_6_p_base_by_risk_segment` (risk_segment → p_reorder_180d)

**This file creates (run in this order)**

1. `churn.v_7a_scenario_params`
2. `churn.v_7a_budget_pool_by_scenario`
3. `churn.v_7a_offer_ev_by_scenario`

**Downstream consumers**

* `churn.v_7a_offer_ev_by_scenario` → Phase 7B allocator (`churn.v4_7_b_budget_allocator_by_scenarios`)
* `churn.v_7a_budget_pool_by_scenario` → Phase 7B allocator + KPI rollups



## Sanity checks to run after build

**7A.1 Scenario table integrity**

```sql
SELECT scenario_id, COUNT(*) AS rows
FROM churn.v_7a_scenario_params
GROUP BY 1
ORDER BY 1;
```

Expected: **exactly 6 scenarios**, each **1 row**.

**7A.2 Budget pool completeness (scenario-month coverage)**

```sql
SELECT scenario_id, COUNT(*) AS scenario_month_rows
FROM churn.v_7a_budget_pool_by_scenario
GROUP BY 1
ORDER BY 1;
```

Expected: all scenarios have the **same number of months** (unless you intentionally filtered months).

**7A.3 EV recompute invariants**

* `BASE` scenario should match baseline math structure (not necessarily equal to net_ev_default in other tables, but internally consistent).

Quick “non-null” coverage:

```sql
SELECT
  scenario_id,
  COUNT(*) AS rows,
  SUM(CASE WHEN p_offer_scn IS NULL THEN 1 ELSE 0 END) AS missing_p_offer,
  SUM(CASE WHEN net_ev_scn IS NULL THEN 1 ELSE 0 END) AS missing_net_ev
FROM churn.v_7a_offer_ev_by_scenario
GROUP BY 1
ORDER BY 1;
```

**7A.4 Offer-type counts stable across scenarios**

```sql
SELECT scenario_id, offer_type, COUNT(*) AS ct
FROM churn.v_7a_offer_ev_by_scenario
GROUP BY 1,2
ORDER BY 1,2;
```

Expected: for each `offer_type`, counts are **identical across scenarios** (scenarios shouldn’t create/drop offers).
