# Phase 7B — Budget allocator + risk buffers + official p95 policy

## Purpose of Phase 7B

Phase 7B converts scenario economics into an **actual decision rule**:

> “Given a budget per month, which customers do we activate under each scenario — and how do we enforce governance against overspending risk?”

This is where the system becomes “decision-ready.”

---

## 7B.1 The allocator view: `churn.v4_7_b_budget_allocator_by_scenarios`

### What it does (high-level)

For each scenario-month:

1. pick **one best offer per customer-anchor**
2. rank customers by value
3. compute running spend curves (expected + worst-case)
4. compute a **risk-aware spend curve** using a p95 buffer
5. apply policy flags + “uh-oh” monitors

---

### Step 0 — one offer per customer anchor (`offers_one_per_customer`)

Because `v_7a_offer_ev_by_scenario` is offer-level, you first reduce to a single chosen offer per customer-anchor per scenario:

Selection logic:

* Maximize `net_ev_scn`
* Tie-break on lowest `offer_cost_scn`
* Tie-break on highest `p_offer_scn` (more confidence)

This prevents double-counting the same customer anchor across multiple offers.

---

### Step 1 — filter to the eligible candidate population

You only allocate to customers who:

* passed the Phase 6 gating (`final_pass = 1`)
* are in the offer candidate pool (`candidate_flag = 1`)
* have positive EV and non-zero cost under the scenario

This ensures the allocator is not spending money on non-actionable / non-eligible rows.

---

### Step 2 — priority ranking (what are we ranking and why?)

`priority_rank` ranks **customers** within each `(scenario_id, decision_month)` by:

* highest `net_ev_scn` first
* lowest `offer_cost_scn` second (cheaper tie-break)

Why: this matches the business goal of **maximizing total value under a hard cash constraint**.

---

### Step 3 — running spend curves

You build three running cumulative curves in order of rank:

* `running_spend_expected` = cumulative sum of `expected_offer_cost_scn`
  (expected cash burn, probabilistic)
* `running_spend_raw` = cumulative sum of `offer_cost_scn`
  (worst case if everyone redeems)
* `running_var` = cumulative cost variance assuming Bernoulli redemption

Variance formula:
[
Var(\text{spend}) = \sum c^2 \cdot p \cdot (1-p)
]

This is what enables risk-aware budgeting.

---

### Step 4 — p95 risk buffer and policy flags

You compute the p95 buffered spend curve:

[
running_spend_{p95} = running_spend_{expected} + z \cdot \sqrt{running_var}
]

Where:

* `z = 1.645` corresponds to **one-sided 95%** (p95 governance level)
* interpretation: “we want to be 95% confident we do not exceed budget”

Then define:

* `selected_flag_no_buffer`: expected spend <= budget (looser)
* `selected_flag_p95_buffer`: **p95 spend <= budget** (official)

---

### Step 5 — month-level “uh-oh” monitors

Even with p95 buffering, you still track tail risk:

* `p95_overspend_*`: should be **0** under official policy
* `raw_overspend_*`: can still occur (allowed but monitored)

This is important governance: you don’t hide risk, you measure it.

---

## 7B.2 `churn.v_7_a_budget_pool_by_scenario_effective` — why it exists

This is the standalone view that computes:

* `risk_buffer_amount`
* `effective_budget_amount = budget_amount - risk_buffer_amount`

It exists because it makes the p95 buffer logic auditable and reusable.

You used conservative handling for missing `p_offer_scn`:

* treat NULL as 1.0 → maximum variance/cost exposure

---

## 7B.3 About `churn.v_7b_budget_risk_monitor`

This was an earlier risk-buffer heuristic based on spend ratios.
You ultimately moved to a more principled buffer model (p95 using variance).

You can keep `v_7b_budget_risk_monitor` as a diagnostic, but the “official” is p95.

---

### Phase 7B outputs (what matters)

This phase yields:

* customer-month-scenario ranked list
* official selection flag (`selected_flag_p95_buffer`)
* governance monitors (p95 overspend should be 0; raw overspend can be >0)

This feeds Phase 7C/7D.

## Sanity checks to run after build

**7B.1 One budget per scenario-month**

```sql
SELECT
  scenario_id,
  decision_month,
  COUNT(DISTINCT budget_amount) AS distinct_budgets
FROM churn.v4_7_b_budget_allocator_by_scenarios
GROUP BY 1,2
HAVING COUNT(DISTINCT budget_amount) > 1;
```

Expected: **0 rows**.

**7B.2 One offer row per customer-anchor per scenario**
*(because you explicitly enforce `offers_one_per_customer`)*

```sql
SELECT
  scenario_id,
  decision_month,
  customer_unique_id,
  anchor_date,
  COUNT(*) AS rows_per_customer_anchor
FROM churn.v4_7_b_budget_allocator_by_scenarios
GROUP BY 1,2,3,4
HAVING COUNT(*) > 1;
```

Expected: **0 rows**.

**7B.3 p95 buffer policy validity (your official rule)**

```sql
SELECT *
FROM churn.v4_7_b_budget_allocator_by_scenarios
WHERE selected_flag_p95_buffer = 1
  AND running_spend_p95 > budget_amount;
```

Expected: **0 rows** (this is your “Test 1” that must stay clean).

**7B.4 Worst-case overspend monitor (allowed)**

```sql
SELECT
  scenario_id,
  decision_month,
  MAX(running_spend_raw) FILTER (WHERE selected_flag_p95_buffer = 1) AS spend_raw_selected,
  MAX(budget_amount) AS budget_amount,
  CASE WHEN MAX(running_spend_raw) FILTER (WHERE selected_flag_p95_buffer = 1) > MAX(budget_amount) THEN 1 ELSE 0 END AS raw_overspend_flag
FROM churn.v4_7_b_budget_allocator_by_scenarios
GROUP BY 1,2
ORDER BY 1,2;
```

Expected: **may show some 1s** (documented as acceptable tail risk).

**7B.5 Budget utilization sanity (no wild ratios)**

```sql
SELECT
  scenario_id,
  decision_month,
  MAX(running_spend_expected) FILTER (WHERE selected_flag_p95_buffer=1) / NULLIF(MAX(budget_amount),0) AS util_expected
FROM churn.v4_7_b_budget_allocator_by_scenarios
GROUP BY 1,2
ORDER BY util_expected DESC
LIMIT 20;
```

Expected: utilization is typically ≤ 1 (can be NULL if no selections that month).
