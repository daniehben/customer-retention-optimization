# Phase 7E — Activation feed for execution

### Purpose

This view exists to create the **operational delivery dataset**:

* only selected customers
* with all the fields required to trigger an action
* plus month-level KPI context for governance

---

## `churn.v7_e_activation_feed_customers`

### What it does

* Starts from the frozen customer decision output (7C)
* Ensures 1 row per `(scenario_id, decision_month, customer_unique_id)` using a last dedupe step
* Joins monthly KPIs (7D)
* Filters to `final_selected_flag = 1`

### Why it’s not “duplicate work”

Even though 7C already tells you who is selected, 7E is the **execution bundle**:

* It attaches KPI context to every row (budget, utilization, flags).
* It becomes the single exportable file for “send this to CRM / activation tool.”
* It reduces BI complexity: one flat table contains everything.

### Output shape

One row per selected customer per month per scenario, including:

* recommended offer
* economics
* decision metadata
* governance KPIs for the month

This feed is also one of the final CSV deliverables.

## Sanity checks to run after build

**7E.1 Feed only contains selected customers**

```sql
SELECT COUNT(*) AS non_selected_rows
FROM churn.v7_e_activation_feed_customers
WHERE final_selected_flag <> 1;
```

Expected: **0**.

**7E.2 Feed matches KPI counts**

```sql
SELECT
  e.scenario_id,
  e.decision_month,
  COUNT(*) AS selected_from_feed,
  MAX(k.selected_customers) AS selected_from_kpi
FROM churn.v7_e_activation_feed_customers e
LEFT JOIN churn.v7d_decision_kpis_scenario_month k
  ON e.scenario_id = k.scenario_id
 AND e.decision_month = k.decision_month
GROUP BY 1,2
HAVING COUNT(*) <> MAX(k.selected_customers);
```

Expected: **0 rows** (this is the exact mismatch you already fixed).

**7E.3 No duplicate customer per scenario-month**

```sql
SELECT
  scenario_id, decision_month, customer_unique_id,
  COUNT(*) AS ct
FROM churn.v7_e_activation_feed_customers
GROUP BY 1,2,3
HAVING COUNT(*) > 1;
```

Expected: **0 rows**.
