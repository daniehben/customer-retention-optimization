# Phase 7C/7D — Freeze the decision output + KPI rollups

## Why these exist

Phase 7B produces a “rich internal scoring table” with many columns.

Phase 7C and 7D transform that into:

* **a stable, minimal decision output** (what operations needs)
* **a stable KPI table** (what leadership needs)

This is the boundary between “engine” and “product.”

---

## 7C `churn.v1_7_c_decision_output_customers` — Freeze the customer-level output

### What it does

* Deduplicates down to **one row per customer anchor per scenario-month** (safety against duplication)
* Freezes the official policy:

  * `final_policy_name = 'p95_buffer'`
  * `final_selected_flag = selected_flag_p95_buffer`

### Why this view matters

This view is the **official decision output contract**.

Everything downstream (activation feed, Tableau, exports) should use this — not the allocator.

### What columns it contains

* Keys: scenario, month, customer, anchor
* Recommendation: `recommended_offer_type`
* Decision: `final_selected_flag`
* Economics: `net_ev_scn`, `incremental_profit_scn`, costs, probabilities
* Governance context: budgets + running spend + monitors
* Explainability: `priority_rank`, `cut_by_buffer_flag`, missing-probability flags

---

## 7D `churn.v7d_decision_kpis_scenario_month` — Monthly KPI rollups

### What it does

Aggregates the policy results by `(scenario_id, decision_month)`:

* volume: number of selected customers
* spend (expected, p95, raw-if-all-redeem)
* value (incremental profit and net EV)
* utilization + ROI
* monitors: p95 overspend flag, raw overspend flag
* data quality: missing `p_offer_scn` rows

### Why this view matters

This is what makes Phase 7 **explainable at management level**.

It answers:

* “How many customers are we activating each month?”
* “How much budget is actually being used?”
* “Do we ever violate governance constraints?”
* “Which scenarios produce the best outcomes?”

This feeds scenario comparison (7F–7I) and activation feed (7E).

## Dependencies / Build Order

**Upstream dependencies (must exist first)**

* Phase 7B allocator: `churn.v4_7_b_budget_allocator_by_scenarios`

**This file creates (run in this order)**

1. `churn.v1_7_c_decision_output_customers` *(frozen customer-level decision contract; official policy = p95_buffer)*
2. `churn.v7d_decision_kpis_scenario_month` *(monthly KPIs per scenario-month)*

**Downstream consumers**

* `churn.v1_7_c_decision_output_customers` → 7E activation feed
* `churn.v7d_decision_kpis_scenario_month` → 7E activation feed + 7F–7I scenario comparison/winner views

## Sanity checks to run after build

**7C.1 Decision output uniqueness (one row per scenario-month-customer-anchor)**

```sql
SELECT
  scenario_id, decision_month, customer_unique_id, anchor_date,
  COUNT(*) AS ct
FROM churn.v1_7_c_decision_output_customers
GROUP BY 1,2,3,4
HAVING COUNT(*) > 1;
```

Expected: **0 rows**.

**7C.2 Only valid flags**

```sql
SELECT
  SUM(CASE WHEN final_selected_flag NOT IN (0,1) OR final_selected_flag IS NULL THEN 1 ELSE 0 END) AS bad_flags
FROM churn.v1_7_c_decision_output_customers;
```

Expected: **0**.

**7D.1 KPI vs allocator selected customer reconciliation**

```sql
SELECT
  a.scenario_id,
  a.decision_month,
  COUNT(DISTINCT a.customer_unique_id) FILTER (WHERE a.selected_flag_p95_buffer=1) AS selected_from_allocator,
  k.selected_customers AS selected_from_kpi
FROM churn.v4_7_b_budget_allocator_by_scenarios a
JOIN churn.v7d_decision_kpis_scenario_month k
  ON a.scenario_id = k.scenario_id
 AND a.decision_month = k.decision_month
GROUP BY 1,2,3,4
HAVING COUNT(DISTINCT a.customer_unique_id) FILTER (WHERE a.selected_flag_p95_buffer=1) <> k.selected_customers;
```

Expected: **0 rows**.

**7D.2 Spend monotonicity sanity**

```sql
SELECT *
FROM churn.v7d_decision_kpis_scenario_month
WHERE spend_p95_selected < spend_expected_selected;
```

Expected: typically **0 rows** (p95 should be ≥ expected when selections exist).
